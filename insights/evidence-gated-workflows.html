Submitted is not the same as verified

The completion screen looked convincing. The evidence record told a different story. This finding turned on one question: what did the server mean when it said the case was submitted?

The screen said done. The record disagreed.

The interesting part was what wasn't there. A research-owned case had reached its ordinary completion screen, yet required supporting artifacts were missing. If this had only been a display error, the finding would have stopped at the interface.

It did not. The source notes also recorded a submitted state in authoritative server responses. The UI and the status flag agreed with each other; the evidence behind them did not. That comparison made the difference between a misleading progress bar and a broken submission rule.

The normal workflow was supposed to collect information and supporting material before moving the case forward. Recording progress without checking that material allowed the case to promise more than its stored data could support.

There was an equally important limit: submitted did not mean approved. The observation did not establish a favorable review decision, downstream access, or an effect on another person's account. The reportable result was the invalid submission state itself, not an assumed chain beyond it.

What the next system would believe

A submission flag is rarely consumed in isolation. A review queue, notification worker, or partner integration may interpret it as a promise that required capture has finished. If each consumer has to rediscover whether the evidence exists, the status is not a reliable contract.

The missing invariant is simple: every required artifact must exist, belong to this case, be finalized, and satisfy the configured capture prerequisites before submission can be recorded. A successful upload request is not enough if its background processing is still pending. An artifact identifier is not enough if it belongs to a different case.

There is a second boundary too. Ready for review and review passed are different facts. Completing capture must not manufacture a favorable decision. The decision should have its own authority, inputs, and audit trail.

Make the evidence decide

A safer design lets the client request an action while the server decides whether its prerequisites hold. Requirements come from a server-owned workflow version. Evidence comes from the authoritative artifact store. Neither is taken from a client's statement that a step is complete.

For the final transition, evaluate the prerequisites against one consistent snapshot. Store that evidence revision with the submission record. If evidence can be removed, replaced, or invalidated later, define how that affects an existing submission instead of leaving the state silently inconsistent.

The state change and its notification should also agree. A transaction with an outbox can commit the submission and an event record together; a worker publishes the event afterward. Consumers still need idempotency because event delivery can repeat. Publishing first and hoping the database update succeeds creates a different version of the same broken promise.

The proposed submission gate

This framework-neutral pseudocode describes the proposed control, not the affected implementation. All names are invented. The lock, evidence reads, update, and outbox insertion need equivalent consistency guarantees in the real storage design.

function submit_for_review(actor, case_id, expected_revision):
    transaction:
        case = load_case_for_update(case_id)
        require permitted(actor, "submit", case)
        require case.revision == expected_revision
        require case.state == "collecting"
        policy = load_server_owned_policy(case.policy_version)
        evidence = load_finalized_evidence(case.id)
        require every_requirement_satisfied(policy, evidence)
        require every_item_belongs_to(case.id, evidence)
        save_submission(case, evidence.revision)
        outbox.record_once(case.id, "ready_for_review")
    return submission_receipt(case.id)

# A review decision is made by a separate authorized process.
# This operation does not set a positive decision.

A production implementation also needs a defined retry contract. An already-completed request should return its existing receipt or a documented conflict, without adding a second submission. A stale request must not silently apply itself to a newer evidence set.

Five checks before closure

Run these against local service fixtures and a test database, with event delivery captured by a stub. They specify how the repaired design should behave; they are not requests to send to a third-party service. For every rejected operation, compare the case, evidence links, and event outbox before and after.

Look behind the status flag

Repairing the gate does not explain records created before the repair. An authorized internal consistency check can flag submitted cases without their required evidence revision. Those cases need review; a missing artifact alone does not prove malicious activity, since retention, processing failures, and migrations can also create discrepancies.

Keep operational signals small and useful: case references, policy versions, rejection reasons, and event identifiers. Do not put supporting files or personal data into routine logs. Track failed prerequisite checks separately from ordinary retries so legitimate network recovery does not look like an integrity incident.

The finding in one sentence

The durable lesson is not to make the progress bar stricter. It is to make the state transition true. Submission should mean the server verified its capture prerequisites. Approval should mean an authorized decision process completed its work. Each downstream consumer should know exactly which promise it is relying on.
