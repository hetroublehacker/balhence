The Password Reset Link That Worked Twice

I expected a successful password change to consume the recovery link. The same controlled link changed the password again.

By Aditya Soni / HeTroubleHackerPublished 7 November 2026Updated 8 November 20266 min read
In this articleThe first resetThe second useControls that matteredTakeaway

Hi people,

I was testing an account recovery flow when one small question changed the whole direction of the review: what happens to the reset link after it has already done its job?

Most of us treat a password reset token like a one-time key. You open the email, choose a new password, and the key should disappear. I had a controlled account and mailbox, so I decided to check that assumption instead of trusting it.

Publication note: This story is reconstructed from private research. The organization, product, routes, identifiers, dates, and UI labels were removed or replaced. Every example below is synthetic. I am not claiming a deployed fix, completed retest, or program acceptance.

The first reset looked completely normal

I requested a recovery email for my own test account, opened the link in a clean browser, and selected password A. The application accepted it. A fresh login with password A worked, while the old password failed.

That positive and negative pair was important. It proved that the password transition had really happened. I was not looking at a friendly success message while the account remained unchanged.

At this point the flow looked secure. Then I returned to the same link.

This is where it became interesting

The used link did not behave like a consumed capability. Its validation step still treated it as active, so I submitted password B through the same recovery flow.

The second change also appeared to succeed. To prove that the account state had moved again, I tested both new passwords from clean sessions. Password B logged in. Password A, which had worked after the first reset, now failed.

That control closed an easy objection. The response was not merely duplicated. The same recovery capability had caused two separate password changes on the same controlled account.

POST /recovery/complete HTTP/1.1
Host: account.research.example
Content-Type: application/json

{"recovery":"[SYNTHETIC_ONE_TIME_VALUE]","new_password":"[PASSWORD_B]"}

HTTP/1.1 200 OK
Content-Type: application/json

{"status":"password_changed"}

The request above is an illustration, not an original capture. The route, fields, values, host, and response have all been replaced.

What the controls proved - and what they did not

I tried the recovery value with a different controlled account identity and it was rejected. That showed the value was tied to the intended account. Later, after its normal lifetime passed, it expired. This was not an indefinitely valid master key.

The issue was narrower: successful use did not immediately consume the capability. During its remaining lifetime, someone who still possessed that link could choose another password after the account owner believed recovery was finished.

This distinction matters when writing a report. I could prove sequential replay and a second credential change. I did not need to claim a permanent bypass or access to anyone else's account.

Why one-time really needs to mean one-time

Recovery links can pass through mail scanners, browser history, support systems, backups, and copied messages. If a link is exposed before the owner uses it, the owner's successful reset should close that window. Expiry alone is not enough because expiry answers when the token becomes invalid, not whether it has already been used.

The safest design is to consume the token atomically with the password change. The server should mark it used before committing the new credential, reject every later validation and reset attempt, and handle two concurrent submissions so only one can win.

I would also keep a deliberately invalid recovery value in the test matrix. It confirms that the application is checking token state, not merely accepting any well-formed value and routing the request by account name.

Takeaway

When I test recovery, I no longer stop at "the new password works." I keep the original link and ask four more questions:

  • Does the token fail immediately after one successful use?
  • Do two simultaneous submissions produce only one change?
  • Does a new reset invalidate older outstanding links?
  • Does a password change invalidate the sessions that should no longer survive?

The interesting bug was not in generating the link. It was in the moment after success, when the system forgot that the link had already spent its authority.

That is all for this write-up. I hope it gives you one extra test for the next account recovery flow you review.
