The draft you could change but could not read

The read was denied. The write persisted. An owner's view of the changed draft gave a permission mismatch a concrete consequence.

A denied read, a changed draft

The account could not read the draft, but it could change its contents. That contradiction is the starting point of the source report: a read restriction held while a separate write path crossed the same ownership boundary.

The baseline involved two controlled accounts. One owned the draft; the other had no permission to read it. The denied read matched that relationship. Unfinished work still belonged to its owner, regardless of whether the draft had reached a consequential step in the workflow.

The decisive observation came from the owner's side. After the separate write, the owner independently saw the changed contents. That check established that the change had been stored. A second operation affecting ordering showed another inconsistency in how draft changes were authorized.

The report therefore supported a specific finding: the tested non-owner could alter another controlled account's draft. The draft identifier was already known. The observations did not demonstrate discovery of unknown identifiers, and no completed, sent, or signed downstream event was established.

The HTTP notebook

The denied read was the useful baseline. It showed that the unrelated account should not have access to the draft. The later state change described above is the finding; this notebook illustrates the read control, not the separate mutation.

A response code alone would not prove the write-side failure. The owner's independent view of changed state supplied that part of the evidence.

What the owner's check established

The owner's observation gave the finding its weight. A success response alone would have left open whether anything changed; the stored edit answered that question. The denied read answered a different question, about a different action. Reading, editing, rearranging, and progressing a draft each need a permission decision connecting the acting account to the specific object and requested action.

Authentication answers who is making the request. A valid anti-CSRF check supports the request's connection to the current browser session. Neither answers whether that account may change this draft. A request can satisfy both controls while crossing an ownership boundary.

The two successful mutation types suggest inconsistent authorization coverage. They do not identify a particular missing function or prove the structure of the underlying code. The design diagnosis is that the effective write policy did not enforce the same ownership boundary as the read policy.

The demonstrated consequence was loss of draft integrity. Later workflow effects would depend on product rules, review requirements, and further permissions. Those possibilities can inform engineering review without being reported as events that occurred.

Closing the authorization gap

The denied read was already doing its job. That protection did not carry over to the tested writes. The proposed repair belongs wherever the application saves a draft change, including operations that rearrange its contents.

Before saving, the server should check whether the signed-in account may perform this action on this draft. Knowing the identifier is not permission to edit it. Every write path should use the same deny-by-default policy, with any referenced section or attachment checked against the authorized draft.

Sharing still needs to work. An invited editor may be allowed to save, while a viewer must remain read-only. Both cases matter: blocking everyone except the owner could stop valid collaboration without proving that every write path is covered.

The retest that matters

A rejected edit must leave the draft's contents, order, version, and pending work unchanged. Check the saved draft, not just the response.

Follow the change into background work

A draft often contains child objects such as sections or attachments. Checking the parent alone is insufficient when a mutation also references children. Every referenced child must belong to the authorized parent and satisfy any additional policy; valid objects from different owners cannot be combined merely because each exists.

If processing continues in a background worker, the authorization boundary must survive that handoff. Queue access or a worker's service identity should not silently substitute for the initiating account's authority. A server-created work item should bind the verified principal, resource, and permitted action, with fresh policy evaluation when the worker applies its result.

Changed ownership, removed sharing, and invalid draft state can invalidate work that was acceptable when queued. The worker should reject an attachment or update when that binding no longer holds. These are proposed design considerations, not evidence that a particular queue or worker caused the observed finding.

What a retest still needs to show

Closure would need evidence from a corrected build that all relevant write paths apply the policy, including ordering, child changes, and any deferred processing. Positive collaboration checks matter alongside denials. This article proposes that verification; it does not claim that a fix has been retested.

The transferable lesson is to review authority at the point where state changes. A protected screen and a protected read are useful controls, but the stored draft depends on every mutation making its own complete authorization decision.
