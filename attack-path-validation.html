Start with evidence

Recurring penetration testing starts with a reliable baseline

A recurring plan is only useful when everyone knows what the earlier assessment covered. The baseline records the agreed application boundary, relevant roles and tenants, critical workflows, APIs, integrations, environment, exclusions and tested version.

After that, each cycle answers a smaller question: what changed, which attack paths deserve another look, which fixes should be verified, and what remains outside the current boundary?

Compare the delivery options on the penetration testing as a service page, or draft a private web or API scope.

The validation model

Attack-path validation across identity, tenants, APIs and AI tools

The work follows the boundaries an attacker would need to cross, not a generic list of checks. Every cycle begins and ends with an explicit decision.

  1. 01 / Define

    Set the boundary

    Record assets, roles, tenants, critical workflows, test identities, authorization and limits.

  2. 02 / Validate

    Prove the path

    Test selected attack paths and manually reproduce issues before they reach the report.

  3. 03 / Remediate

    Keep context attached

    Connect evidence, severity reasoning, ownership and practical remediation to each finding.

  4. 04 / Re-test

    Check the change

    Verify agreed fixes and controls against the version actually tested, then record the result.

Accountable delivery

A human review gate before findings reach your team

Automation may support research, repeatable checks and evidence organization. A researcher remains responsible for scope, safe execution, impact validation, severity and delivery.

Candidate observations do not become reported findings until they have been reproduced, checked against scope, reviewed for impact and prepared with evidence your engineers can follow.

One connected record

Evidence that stays connected to remediation and re-testing

The goal is not another dashboard. It is a usable chain from the approved boundary to a confirmed issue, the fix decision and the result of checking that fix.

SCOPE

Versioned boundary

Assets, roles, tenants, workflows, accounts, exclusions and test limits for the current cycle.

PROOF

Reproducible evidence

Steps, requests, responses and impact notes with secrets and unrelated data redacted.

DECISION

Remediation ownership

Severity reasoning, recommended action, owner, status and open questions kept with the finding.

VERIFY

Re-test history

The version checked, evidence from the re-test and a clear fixed, partial, open or not-tested result.

Bounded by design

Safety controls for every testing cycle

Recurring work does not create standing permission to test anything at any time. Each cycle has a written boundary and stop conditions.

Required before testing

  • Versioned target and environment list
  • Controlled identities and synthetic test data where practical
  • Approved actions, request limits and testing window
  • Emergency contact, stop conditions and escalation path
  • Data handling, retention and AI-use decisions

Excluded by default

  • Denial of service and destructive actions
  • Persistence or lateral movement outside the agreed boundary
  • Social engineering and physical testing
  • Access to real customer data beyond minimum safe proof
  • Testing third-party assets without their authorization

Recurring security validation FAQ

Is this an autonomous penetration testing platform?

No. Current delivery is specialist-led. Automation may support approved research, repeatable checks and evidence organization, but it does not expand scope or replace human validation.

What is available now?

Baseline web, API, SaaS and AI application assessments are available by scope. Scheduled change cycles and re-tests can follow a baseline when capacity, access and authorization are agreed.

What is the design-partner program?

Selected teams can help shape a planned shared workflow that keeps scope, evidence, finding status, remediation ownership and re-test decisions connected. This workflow is in development; availability and features are confirmed during the design-partner conversation.

Does recurring validation mean continuous or 24-hour testing?

No. Testing happens in agreed windows against a written boundary. The cadence, response expectations and work reserved for each cycle are defined in the engagement agreement.
